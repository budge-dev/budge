# Budge v1 spec (draft for review)

Status: draft, 2026-10-25. Nothing is built.

Budge finds a meeting time for a small group of people who don't share a
calendar system. An organiser names the people and a rough window. Budge
then:
- emails each person;
- reads their answers;
- sends at most two reminders;
- brings the organiser only the decisions that need them;
- books on the organiser's own calendar once they approve.

Companion files:
- [templates.md](templates.md): every email Budge sends.
- [tests.md](tests.md): acceptance tests.
- [archive/](archive/): superseded drafts.

## 0. Principles

1. **The language model only reads.**
   - It turns one person's free-text reply into structured constraints.
   - It never picks a time, never writes outbound text, has no tools, and
     never sees another person's data.
2. **A deterministic solver ranks times.**
3. **The organiser approves every booking.** v1 never books on its own.
4. **Code, not prompts, decides who sees what.**
   - Invitees see counts, and only after they answer.
   - The organiser sees who is pending and the trade-offs.
   - Nobody sees anyone's calendar.
5. **Every email says it comes from an AI scheduling assistant**, names
   the organiser, explains why it was sent, and offers a global opt-out.
6. **Unknown stays unknown.**
   - Silence is not "no".
   - "Maybe" is tentative.
   - Availability is not consent to book.

## 1. Scope of v1

- **Organiser:** a Google Calendar user. One organiser per meeting.
- **Size:** 3 to 8 people including the organiser.
- **Meeting:** one-off; length 15 to 240 minutes; a window of at most 6
  weeks.
- **Language:** English.
- **Answers:** by email reply or the private answer page. Invitees never
  connect a calendar.
- **Not in v1:**
  - Microsoft;
  - recurring meetings;
  - calendar holds;
  - slots shared between pending meetings;
  - inferred priority;
  - automatic re-planning;
  - saved invitee rules;
  - an MCP or WebMCP endpoint;
  - one-to-one agent booking;
  - chat apps.

## 2. Actors and identity

| Actor | Identity | Can |
|---|---|---|
| Organiser | Email verified by magic link; Google OAuth for their calendar | Create, edit, pause, cancel meetings; answer decision cards; approve bookings |
| Invitee | The address the organiser entered; a signed per-invitee link; a signed reply address | Answer, correct, propose a time, step out, stop all Budge email |
| Delegate | Any other sender replying in the thread | Nothing until the organiser or the invitee confirms the delegation |
| Operator (Ao) | Admin account with 2FA | Read status, take over a meeting, pause all sending |

## 3. Time

- **On the wire:** RFC 3339 in UTC. Zones are IANA names.
- **Display:** every time shown to a person carries the date, local time,
  zone and UTC offset in that person's zone.
- **Invitee zone,** in this order:
  1. The browser, when they open the page (`confirmed`).
  2. The organiser's entry (`organiser`).
  3. A guess from the reply's `Date` header offset (`guessed`).
  4. Otherwise the organiser's zone (`unknown`).
  A `guessed` or `unknown` zone is shown in the echo confirmation.
- **DST:** a local time that is ambiguous or doesn't exist is rejected,
  never silently moved.
- **Candidate grid:** 30-minute steps inside the organiser's working hours
  (default Mon to Fri 09:00 to 18:00 in their zone, editable per meeting).
- **Working days** for reminders: Mon to Fri in the recipient's zone.

## 4. Data model

SQLite through Drizzle. All ids are random 128-bit values. `*_utc` columns
hold UTC instants.

```ts
organiser   { id, email, name, tz, status: 'active'|'limited'|'suspended',
              caps: { activeMeetings: 3, recipients: 15 }, createdAt }

google_auth { organiserId, scopes[], accessTokenEnc, refreshTokenEnc,
              expiresAt, revokedAt? }

meeting     { id, organiserId, title, durationMin,
              mode: 'remote'|'in_person'|'either', location?,
              windowStartUtc, windowEndUtc, workingHours,
              status: MeetingState, version, deadlineUtc?,
              bookedReservationId?, createdAt }

invitee     { id, meetingId, email, name?, role: 'essential'|'optional',
              tz?, tzSource: 'confirmed'|'organiser'|'guessed'|'unknown',
              state: InviteeState, linkKeyId, steppedOutAt?,
              delegateFor?: inviteeId }

answer      { id, inviteeId, meetingVersion,
              source: 'page'|'reply'|'organiser_entry'|'delegate',
              status: 'unconfirmed'|'confirmed'|'superseded'|'rejected',
              inboundMessageId?, createdAt, confirmedAt? }

constraint  { id, answerId,
              kind: 'hard_no'|'hard_yes'|'preference'|'tentative'|'authority',
              scope: { dates?: DateRange[], weekdays?: number[],
                       localTime?: {from:'HH:MM', to:'HH:MM'}, tz },
              weight?: -2..2, evidence: string /* quoted span */ }

slot        { id, meetingId, startUtc, endUtc, meetingVersion }   // candidate grid row
slot_answer { slotId, inviteeId, value: 'yes'|'no'|'tentative'|'unknown',
              pref: -2..2 }                                         // derived, rebuilt by solver

claim       { id, organiserId, meetingId, startUtc, endUtc,
              kind: 'offer'|'reservation',
              state: 'active'|'released'|'expired', expiresAtUtc,
              version }

reservation { id, claimId, meetingId, startUtc, endUtc,
              state: 'committing'|'confirmed'|'uncertain'|'repair_required'|'released',
              leaseExpiresAtUtc, googleEventId /* chosen by Budge */, version }

decision    { id, meetingId, kind: DecisionKind, options: Option[],
              state: 'open'|'resolved'|'stale'|'expired',
              createdAt, resolvedAt?, resolvedOption?, basedOnVersion }

message     { id, meetingId?, inviteeId?, direction: 'out'|'in',
              template?: TemplateId, providerId?, status, createdAt,
              rawRef? /* inbound raw text, deleted with the meeting */ }

outbox      { id, messageId, idempotencyKey UNIQUE,
              status: 'pending'|'sent'|'failed'|'suppressed', attempts, nextAttemptAt }

job         { id, kind, runAtUtc, payload, idempotencyKey UNIQUE,
              attempts, lockedUntil?, status }

suppression { emailHash /* HMAC-SHA256 of lowercased address */,
              reason: 'unsubscribe'|'bounce'|'complaint'|'abuse', createdAt }

audit       { id, meetingId?, actor: 'system'|'organiser'|'invitee'|'operator',
              event, data /* minimal, no reply text */, at }
```

## 5. State machines

### Meeting

```
draft --organiser confirms spec--> collecting
collecting --decision needed--> deciding
deciding --organiser picks a time--> booking
deciding --organiser changes people/window--> collecting (version+1)
booking --reservation confirmed--> booked
booking --reservation uncertain/repair--> needs_repair --operator/organiser--> booked | collecting
booked --decline by essential--> deciding (card: keep / make optional / re-plan)
booked --organiser approves re-plan--> collecting (version+1)
booked --meeting end passes--> done
any --organiser--> paused --organiser--> previous state
any --organiser--> cancelled
done | cancelled --30 days--> deleted
```

A **decision is needed** when any of these happens:
1. Every essential invitee has a confirmed answer, and at least one slot
   works for all essentials.
2. Every essential invitee has answered, and no slot works for all
   essentials.
3. An invitee reaches `no_reply`.
4. An essential invitee steps out.
5. The parser flags something only the organiser can settle: a Calendly
   link, a delegate, a question to the organiser.
6. The window closes.

### Invitee

```
invited --2 working days, no answer--> reminded_1
reminded_1 --2 working days--> reminded_2
reminded_2 --2 working days--> no_reply (organiser decision)
any active --reply or page answer--> answered_unconfirmed --confirm--> answered
answered --new answer--> answered_unconfirmed (old answer superseded)
any --step out--> stepped_out
any --global unsubscribe, bounce, complaint--> unreachable
```

Rules:
- Page answers count as confirmed straight away.
- Reply answers wait for the echo confirmation (template T2).
- An organiser entry counts as confirmed, marked `organiser_entry`.
- Reminders are never sent to `answered_unconfirmed`, `answered`,
  `stepped_out` or `unreachable` invitees.

### Reservation

```
committing --calendar insert OK--> confirmed
committing --error with known outcome (4xx)--> released
committing --timeout / unknown outcome--> uncertain
uncertain --reconcile finds our event--> confirmed
uncertain --reconcile finds nothing after N tries--> released
confirmed --reconcile finds event deleted or moved--> repair_required
committing --lease expires--> released
```

## 6. The ledger (concurrency)

The ledger is the `claim` table: the organiser's time that Budge has
promised to a meeting.

1. **Offers are exclusive and few.**
   - An `offer` claim is created only when Budge names concrete times to
     people: the three times in reminder 2 (T4), and the times on a
     decision card.
   - A meeting holds at most 3 active offers.
   - Offers expire after 72 hours.
   - The open grid on the answer page is not a claim. It collects
     availability, not promises.
2. **Claiming is a short transaction.**
   - `BEGIN IMMEDIATE`, check that no active claim of the same organiser
     overlaps `[start, end)`, insert, `COMMIT`.
   - No network call ever happens inside a transaction.
3. **Every claim and every booking re-checks the live calendar.**
   - Google free/busy is read just before an offer is made, when a
     decision card is created, and again when the organiser taps it.
   - A slot that has become busy turns the card `stale`. The organiser
     sees "this time was just taken" and the next options.
4. **Counter-proposals go through the same path.**
   - A time an invitee proposes outside the offered set gets a claim
     check and a free/busy check.
   - It is shown to the organiser as an option and never accepted
     automatically.
5. **Booking takes three steps** (the Reservation machine above):
   1. Short transaction: turn the meeting's chosen offer into a
      `reservation` in state `committing`. It gets a lease (5 minutes), a
      version, and a `googleEventId` generated now, so that a retry
      inserts the same event.
   2. Outside any transaction: `events.insert` with that id and
      `sendUpdates=all`.
   3. Short transaction: `confirmed` (or `uncertain`, or `released`).
      Release the meeting's other offers, and send T5 to invitees who had
      picked a released offer.
6. **Reconciliation.**
   - A job runs every 15 minutes.
   - It compares every `uncertain` and `confirmed` reservation with
     `events.get` on its id.
   - Mismatches become `repair_required`, with a decision card to the
     organiser and an operator alert.
7. **Booked meetings are never moved without the organiser.**

**The guarantee:** Budge never commits two meetings to overlapping time.
Conflicts that start outside Budge are detected and repaired, not
prevented.

## 7. Solver

**Input:** the slot grid for the current meeting version, each invitee's
confirmed constraints, and the organiser's live free/busy minus other
meetings' active claims.

**Per slot and invitee:**
1. Apply the constraints in order: `hard_no` gives `no`; `hard_yes` gives
   `yes`; `tentative` gives `tentative`; `preference` sets `pref`.
2. Anything still unset is `unknown`.
3. If a `hard_no` and a `hard_yes` overlap on a slot, the slot is
   `tentative` and the answer is flagged.

**Ranking:** sort by
1. all essentials `yes` (descending);
2. number of essentials `tentative` (ascending);
3. optional `no` count (ascending);
4. `unknown` count (ascending);
5. preference sum (descending);
6. start time (ascending).

**Output:**
- The top 3 slots, each with a one-line reason built from counts, such as
  "all 5; Dee prefers mornings" or "4 of 5, without Ben (optional)".
- Optionally a fallback, such as "extend the window by 1 week", "make X
  optional" or "allow remote".

The solver is a pure function and is tested with fixtures. It never calls
the model.

## 8. Reply parsing

**Inbound pipeline:**
1. Verify the provider's webhook signature.
2. Match the HMAC-signed reply address `r+<meeting>.<invitee>.<sig>@reply.usebudge.dev`.
   Wrong or missing signatures go to the operator queue.
3. Detect autoreplies (`Auto-Submitted` other than `no`, `X-Autoreply`,
   `Precedence: bulk|auto_reply`, common out-of-office subjects).
   Autoreplies never count as answers. A "back on <date>" becomes a
   suggested `hard_no` that needs confirmation.
4. Check the sender: if it isn't the invitee's address, the reply becomes
   a delegate answer awaiting confirmation.
5. Strip quoted history, signatures and attachments.
6. Call the model.

**Model call:** `claude-haiku-5-5`, falling back to `claude-sonnet-5-5`
when the output fails the schema twice. No tools.

The system prompt says the reply text is data. The input holds today's
date, the meeting window, the invitee's zone and its source, and the
reply text only.

**Output schema** (zod), validated strictly:

```ts
{
  constraints: Array<{ kind: 'hard_no'|'hard_yes'|'preference'|'tentative',
                       scope: Scope, weight?: number, evidence: string }>,
  steppedOut: boolean,
  delegateFor?: string,            // "I'm answering for my boss"
  calendlyUrl?: string,            // any scheduling link in the reply
  outOfOfficeUntil?: string,       // ISO date
  questionForOrganiser?: string,   // ≤200 chars, copied as plain text
  understood: boolean              // false: nothing usable
}
```

**After parsing:**
- Each `evidence` must be a substring of the cleaned reply, or the
  constraint is dropped.
- Template T2 echoes the constraints back as plain sentences built in code
  from the schema, not by the model.
- If `understood` is false, the invitee gets T2 with "I couldn't read
  times from your reply" and the page link.
- A Calendly link, a delegate, or a question to the organiser becomes a
  decision for the organiser.

## 9. Email

**Templates** are listed in [templates.md](templates.md). Outbound text is
only ever a template filled with fields from the database.

**Sending:**
- **From:** `Budge for <organiser name> <meet@mail.usebudge.dev>`.
  Reply-To is the signed reply address.
- **Organiser cc:** on T1 only.
- **Headers:** `List-Unsubscribe` with a one-click URL and
  `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058).
- **DNS:** SPF, DKIM and DMARC on `mail.usebudge.dev`.
- **Before every send,** the outbox checks:
  - the suppression list;
  - the organiser's caps;
  - the global send switch;
  - that the invitee is in a sendable state;
  - that the meeting isn't paused or cancelled.
- **Limits:**
  - At most one invitation and two reminders per invitee per meeting
    version.
  - Echo confirmations (T2) are sent only in reply to the invitee's own
    message.
  - T5 only when an invitee's picked time is withdrawn.
- **Caps for new organisers:**
  - 3 active meetings and 15 recipients across them.
  - Raised by the operator.
- **Suppression:**
  - Hard bounces and spam complaints from provider webhooks suppress the
    address for all organisers.
  - A complaint also pauses that organiser for review.
- **Alerts and emergency stop:**
  - Alert at 0.05% complaint rate or a 5% bounce rate over a rolling
    window.
  - A config flag halts all outbound sending.
- **Provider:** to be chosen once one approves the samples in writing (see
  the Budge planning notes). The code talks to one small `Mailer`
  interface.

**Organiser-facing emails** (O1 to O4 in templates.md) go only to the
signed-up organiser.

## 10. Google Calendar

- **Scopes**, sensitive and needing verification:
  - read the organiser's free/busy;
  - create and read events on calendars they own.
  - Candidate scope names: `calendar.freebusy` and
    `calendar.events.owned`. Verify against Google's current scope list
    before submitting.
  - No Gmail scopes.
- **Free/busy:** `freebusy.query` on the organiser's primary calendar,
  plus any calendars they tick.
- **Booking:** `events.insert` on the primary calendar:
  - the client-chosen `id` (base32hex);
  - `sendUpdates=all`;
  - attendees = organiser plus invitees not stepped out;
  - a Meet link only if the organiser turned it on (`conferenceData` with
    a stable `requestId`);
  - the description says it was arranged with Budge.
- **Watching:** `events.get` every 30 minutes until the meeting ends, and
  before any card. An attendee `responseStatus` of `declined` triggers
  the decline flow. Push channels are optional later; polling is the
  baseline.
- **Revoked or expired auth:** pause the meeting and email the organiser
  (O4).

## 11. Surfaces

**Organiser web:**
- Sign-in.
- Connecting Google.
- Creating a meeting: a text box, or forwarding an email to
  `<handle>@new.usebudge.dev`.
- The confirmation card.
- The meeting status page: invitees, states, next reminder, decision
  list.
- Pause, cancel and edit.
- Settings: working hours, zone, Meet on/off.
- Account deletion and export.

**Invitee page** `/m/<signed token>`:
- A `GET` shows the page. It never changes state, so mail scanners can
  safely prefetch it.
- `POST` with a CSRF token bound to the link: pick slots, "none of these
  work", propose a time, step out, confirm or fix a parsed answer.
- Counts per slot appear only after this invitee has answered.
- Links expire 30 days after the meeting; keys can be rotated.

**Operator** (Ao): read-only meeting view, take over (pause automation
and edit answers), global send switch, raise caps, suppression lookup.

**Webhooks:** inbound mail, bounces and complaints. Each verifies the
provider's signature.

## 12. Reliability

- **One Fly.io machine** in London (lhr) runs web, webhooks and jobs, with
  SQLite on a volume and Litestream backing up continuously to object
  storage.
- **Jobs** are rows with `runAtUtc` and an idempotency key. On boot the
  worker runs every overdue job once, so missed reminders are sent late,
  never twice.
- **Outbox:** emails are written in the same transaction as the state
  change that causes them, then sent by the worker. The idempotency key is
  `<meetingId>:<inviteeId>:<template>:<version>`.
- **Litestream** can lose the last seconds of writes. After a restore,
  reconciliation and outbox idempotency stop duplicate events and
  duplicate emails.
- **Restore drill** before launch: restore a backup into a scratch app and
  run reconciliation.

## 13. Privacy and retention

**Roles** follow the drafted DPA: the organiser is controller and Budge
processor for meeting data. Budge is controller for organiser accounts,
the suppression list and security logs.

**Retention, run nightly:**
- Meeting, invitees, answers, constraints, messages and raw inbound text:
  deleted 30 days after the meeting ends or is cancelled.
- Audit rows for the meeting: cut down to counts at the same time.
- Security logs: 90 days.
- Backups: 30 days.
- Suppression hashes: kept until the person asks.

Tokens are encrypted with an application key that is held apart from the
database. Logs never contain reply text.

## 14. Metrics

Recorded per meeting, without reply text:
- time from Start to booked;
- organiser actions after creation;
- answers before the first reminder;
- parses corrected by invitees;
- operator takeovers;
- complaints and bounces;
- whether the organiser creates another meeting within 60 days.

These feed the launch gate and the kill criteria in the project plan.

## 15. Open questions for review

1. **Holding offers.** Are 72-hour offers and at most 3 per meeting right?
2. **Where the decision list lives.** Should it be emailed to the
   organiser daily, or only shown on the status page plus an email when
   something new needs them?
3. **Late answers after booking.** Should an invitee who answers after
   the booking be told the chosen time, or left to the calendar invite
   only? The current spec relies on the invite only.
4. **The grid on the answer page.** Should it show all 30-minute slots in
   the window, or a solver-trimmed set (for example the 12 best)?
5. **Forwarded intake.** Should the forwarded-email address
   (`<handle>@new.usebudge.dev`) be in v1, or the web box only?
